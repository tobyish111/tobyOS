# Browser stage 13H — TLS certificate validation

Branch `kernel-tls-certs`, stacked on `browser-canvas` (13I). **The one
true must-have for a shippable browser.** Until now `src/tls.c` accepted
*any* server certificate — every HTTPS connection was trivially
MITM-able. This makes tobyOS actually verify who it's talking to.

## Why both halves are required
X.509 chain validation *alone* is worthless: an attacker can present any
real, publicly-obtainable certificate chain for the target site. The
binding to the live connection is **CertificateVerify** — in TLS 1.3 the
server signs the handshake transcript with the leaf certificate's private
key. So validation is two steps, both mandatory:
1. **Chain validation** — the leaf chains to a trusted root, the hostname
   matches (SAN/CN), and nothing is expired → yields the leaf public key.
2. **CertificateVerify** — verify the transcript signature with that key,
   proving the peer actually holds the private key.

Fail either → the handshake is refused (fail closed).

## What shipped
- **Vendored BearSSL** (`third_party/bearssl/`) — the decode/verify-only
  subset of the reference TLS library: its `x509_minimal` chain engine +
  the i31 bignum, RSA (PKCS#1 + PSS verify), EC (P-256/384/521 + ECDSA),
  SHA-1/224/256/384/512 + MD5, and codec. The kernel had **no** RSA,
  ECDSA, ASN.1, or bignum — hand-rolling that for a security path is an
  anti-pattern, so a proven library was the right call. ~55 objects,
  all compile freestanding with one `<string.h>` shim (→ klibc); no
  intrinsics/`__int128` (the SIMD files are gated by
  `BR_ENABLE_INTRINSICS`, which the portable subset never defines).
- **Trust store** — 121 Mozilla root CAs (RSA + EC), generated by
  BearSSL's own `brssl ta` from the curl.se CA bundle into
  `third_party/bearssl/trust_anchors.inc`; `src/tls_trust.c` exposes them.
- **`src/tls.c`** now, in the TLS 1.3 handshake:
  - parses the Certificate message and runs `br_x509_minimal` with the SNI
    hostname + current RTC time (`rtc_unix_time()`), recovering the leaf
    public key;
  - snapshots the pre-CertificateVerify transcript and verifies the
    CertificateVerify signature with that key — ECDSA (P-256/384/521) and
    RSA-PSS (SHA-256/384), the schemes TLS 1.3 uses (the ClientHello's
    `signature_algorithms` now advertises exactly these);
  - refuses a flight that skipped Certificate/CertificateVerify;
  - fails closed on any failure (`TLS_ERR_CERT`).
- **Browser** — a distinct `HTTP_ERR_CERT` flows from `http.c` (on a
  `TLS_ERR_CERT` connect) through the async worker to a dedicated
  **"Your connection is not private"** security page. A cert failure is
  definitive, so the omnibox does **not** downgrade to `http://` or walk
  the www ladder — it shows the page immediately.
- **`tcp_abort()`** (`src/tcp.c`) — an abortive RST close. Rejecting a
  cert aborts the handshake mid-flight, which made us the *active* closer;
  `tcp_close` then blocked in the TIME_WAIT linger and hung the fetch
  worker. `tls_connect` now RST-closes a failed handshake, so the error
  surfaces immediately.

## Verified (QEMU)
- **Accept valid**: `https://www.google.com` renders — serial shows
  `[tls] certificate chain + CertificateVerify OK` (ECDSA leaf).
- **Reject untrusted / self-signed**: local HTTPS server with a
  self-signed cert (completes negotiation — OpenSSL speaks our
  ChaCha20/X25519) → `[tls] CERT chain INVALID: x509 error 56`
  (NOT_TRUSTED) → refused, the "Your connection is not private" page
  renders, and the server's page never loads (no leak).
- **Reject expired**: local server with a cert `notAfter` in 2020 →
  `x509 error 54` (EXPIRED) → refused, security page.
- Both bad-cert cases fail fast (~1.4 s apart, no hang) thanks to
  `tcp_abort`.

## v1 limits
- One cipher suite / one group (TLS_CHACHA20_POLY1305_SHA256 + X25519) —
  unchanged from before; servers that don't offer these fail at
  ClientHello (a pre-existing limit, unrelated to cert validation).
- CertificateVerify supports ECDSA P-256/384/521 and RSA-PSS SHA-256/384
  (the TLS 1.3 set); no RSA-PKCS#1 (which TLS 1.3 forbids for CV anyway).
- No OCSP / CRL revocation checking, no SCT/CT enforcement, no
  name-constraints beyond what `x509_minimal` does.
- The trust store is a fixed built-in bundle (121 roots); no user-managed
  store, no click-through override (fail closed, by design).
- A Certificate message spanning multiple TLS records isn't reassembled
  (rare; the whole flight fits one 16 KiB record for the sites tested).
